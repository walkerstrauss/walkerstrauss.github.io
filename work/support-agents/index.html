Problem

Two support teams had to see what an agent would do on their tickets before it could act on one.

Each team wanted its agent moved onto a new agent platform, inside the ticketing system it already used. Each agent worked against the customer’s own systems: accounts, transactions, statements. I had first built two reference agents that work this way on mock records.

Decision 1

Each requirement became a decision the agent makes on a ticket.

I asked each team to describe its requirements as the set of states a user can be in, and flagged the cases that didn’t fit one. A status question might need account verification first; some cases needed a handoff to a person. For the second agent I scoped the requirements from scratch, which surfaced behavior the agent still needed, such as when to close a ticket.

Decision 2 · Ticketing integration

I tested the integration inside each customer’s own ticketing system, with their engineers.

I tested the integration and worked with each customer to set up the webhook calls from their help desk to the agent’s endpoints. I worked with customer engineers to set up test accounts and map their API responses to the states the agent had to recognize.

Decision 3

Every reply was checked against what the agent actually did.

A reply can read well and still come from the wrong decision, and guessing from the wording leads to fix-and-retry loops that teach nobody how the agent behaves. So each test checked what the agent decided, what it looked up, and whether anything would change.

Decision 4

Before release, each team reviewed the agent’s proposed replies to its own tickets.

I replayed each customer’s existing tickets through the agent, presented the results to their team, and revised it over rounds of feedback. What gave the teams the confidence to deploy was seeing how the agent would answer their own tickets, with nothing sent.

Migrations

I also drove customer migrations onto the platform.

Across those migrations, inference cost fell by more than half.
