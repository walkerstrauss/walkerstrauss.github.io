Problem

In financial services and HR, a request ends in a record.

Many support conversations end with an answer or a handoff to a person. A dispute or a leave request ends with something written to a company system, so the agent has to read the person’s own records, apply the company’s policy, and only then write.

The person wants something done: a charge disputed, time off booked. If it can’t be done, they need the reason and a next step.

Research

Before building, I specified how leave policy works.

The HR agents I reviewed collected a request and passed it on. Whether it met policy was decided later, by someone else.

So I wrote the policy data the agent decides with. Every policy sets its own notice, units and limits, and the rules are written once against whichever policy applies, so the agent can check before it writes.

Who decides

The model reads the request. Code decides whether a rule is met.

Here a wrong answer is a wrong record, so each decision goes to whichever of the three can be held to it.

The model
Reads what the person asked for and words the reply.
Code
Checks the policy and allows or blocks the write.
The person
Confirms before anything is written.
Decision 1

The agent checks a request before it writes anything.

The request stays a draft until a rule has read it against the employee’s own balance and policy.

Decision 2

A block shows the rule, its inputs and a way forward.

With the rule and the numbers in the reply, the employee knows what to change.

Decision 3

An edit updates the same draft.

The start date stays. The days are recalculated, the same check runs again, and nothing is written until the employee says yes.

Decision 4 · A second domain

In a card dispute, the reason decides what the agent asks.

Each dispute reason needs different facts. A missing one blocks the filing and becomes the next question.

Result

Three runs of the same request gave the same decision.

The reply’s wording varies from run to run. The decision and the write do not. In the demos, the same request produced the same decision every time.

Outcome

I built these agents on mock records.

I ran both agents on mock records and services, a separate copy for each session, so they could act on realistic accounts before any customer opened a real system.
